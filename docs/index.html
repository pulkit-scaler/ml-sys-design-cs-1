The Feed Lab Toolkit

Redis, Kafka, Prometheus and Grafana, and the one job each does in a running recommender

  • Reading time about 20 minutes
  • Read before Personalised Recommendation and Feed Ranking
  • Needs nothing installed

Abstract

The feed ranking class ends with a live demo of a small but real feed. It runs as eight services and a one-off setup job, all on one machine. You already know the machine learning parts of it from the class. Four of its tools are new. Redis holds features and answers lookups in a fraction of a millisecond. Kafka keeps every user action in order, so nothing is lost when a reader stops. Prometheus collects numbers from every service every two seconds. Grafana draws those numbers as live charts.

This paper explains each tool in plain words. It covers what problem the tool solves, the few ideas the demo relies on, and what you will see in the lab. Every "In the lab" panel shows real output from the running system. You do not need to run anything to follow it, but the commands are there if you want to.

Keywords  online feature store, key-value store, time to live, event log, topic, offset, retention, metrics, time series, scraping, histogram, dashboard

1Why a running system needs these four

A trained model is a file. A feed is a service that answers millions of requests, remembers what each person just did, and tells its team when something goes wrong. The model is one part of it. The rest is plumbing, and in a feed most of that plumbing does one of three jobs.

The first job is to fetch facts fast. Each request needs the user's taste, their session so far and the features of about two thousand items. It needs them in a few milliseconds. That is Redis.

The second job is to move events reliably. When someone hides a video, that action must reach every part of the system that cares, even if one of those parts is down for a minute. That is Kafka.

The third job is to watch the whole thing. You need to know how slow each step is, how often the system fell back to its safety net, and whether any work is piling up. Prometheus collects those numbers, and Grafana shows them.

2Redis, the online feature store

In the MLOps module you used an online feature store to read one entity's newest features in milliseconds at prediction time. Redis is a common engine for exactly that job. Here is what makes it fast and how the lab uses it.

2.1Data in memory, found by key

Redis keeps its data in memory, not on disk.1 Memory is far faster to read than a disk, so a lookup takes a fraction of a millisecond. The price is that memory is smaller and costs more per gigabyte, so you keep there only what requests need right now.

Every item in Redis has a unique key, a name such as u:42.1 You ask for a key and get its value back. There are no tables and no joins. If you know the key, the answer is immediate. If you do not know the key, Redis is the wrong tool.

2.2Three kinds of value

A value is not only a plain string. Redis offers several data types, and the lab uses three of them.2

Table 1. The Redis keys in the lab.
KeyTypeWhat it holds
u:42StringUser 42's long-term taste and personal vector, packed as numbers
i:715515StringFive features of one item, such as its topic and click rate
s:505HashUser 505's session, one field per topic they engaged with or hid
seen:505SetItems user 505 has already been shown, so they are not shown twice

A hash is a record of field and value pairs under one key, like a small dictionary. A set is a collection of unique values with no order.2 The session is a hash because the stream worker adds one to a single field, such as "hid topic 1", without reading the rest. The seen list is a set because the only question asked of it is "is this item in here?".

2.3Keys that expire

You can give a key a time to live. When it runs out, Redis deletes the key by itself.3 The lab gives each session 1,800 seconds, and the clock restarts with every new action. So a session ends 30 minutes after the user's last action, with no cleanup job. The seen set lives for an hour.

2.4What happens on a restart

Data in memory is lost when the process stops. Redis can save to disk, either as a snapshot every so often or by logging every write, and it can also run with no saving at all.4 The lab turns saving off, because a one-off job rebuilds every user and item record in about a second. A production feature store usually keeps saving on and runs copies on other machines, because rebuilding hundreds of millions of records takes far longer.

In the lab

After the class's freshness demo, where user 505 hides three items from topic 1, Redis holds the following. Run these from the lab folder.

# how many keys: 1M items, 100k users, a few more
docker compose exec redis redis-cli DBSIZE
(integer) 1100007
# user 505's session: three hides on topic 1
docker compose exec redis redis-cli HGETALL s:505
1) "h:1"
2) "3"
# seconds until the session expires
docker compose exec redis redis-cli TTL s:505
(integer) 1800
# the seen set after two pages of 20
docker compose exec redis redis-cli SCARD seen:505
(integer) 40

3Kafka, the event log

Redis answers "what is true now?". Kafka answers a different question, "what happened, and in what order?". A feed needs both.

3.1Events, producers and consumers

An event is a record that something happened, such as a user hiding an item. In Kafka an event has a key, a value and a timestamp.5 A program that writes events is a producer, and a program that reads them is a consumer. Producers and consumers never talk to each other directly. The producer writes and moves on, and any number of consumers read when they are ready.

Events are grouped into named topics.5 The lab has two. The topic events holds user actions, and impressions holds every page the feed served.

3.2Reading does not delete

This is the idea the demo depends on. In a simple queue, taking a message out removes it. In Kafka, events are not deleted when they are read.5 Each topic keeps its events for a set time, and each consumer keeps its own position, called its offset. Reading moves the offset forward and leaves the event where it is.

Two useful things follow. If a consumer stops, nothing is lost. Events pile up in the log, and when the consumer restarts it carries on from its offset. The class shows this live. Also, events can be read as often as needed.5 A new job can replay last week's actions to rebuild a feature or to create training labels.

3.3Why not write actions straight into Redis?

The feed service could update the session in Redis itself. Putting a log in between costs one extra hop and buys three things. Several jobs can read the same actions without the feed knowing about them, such as session features, training labels and monitoring. A burst of traffic waits in the log instead of overloading a slow reader. And the history can be replayed when a job is fixed or added.

In the lab

The lab runs Redpanda, a separate product that speaks Kafka's protocol, so its command-line tool is rpk.6

# the two topics
docker compose exec redpanda rpk topic list
NAME         PARTITIONS  REPLICAS
events       3           1
impressions  3           1
# the first two events ever written, read again from the start
docker compose exec redpanda rpk topic consume events --num 2 --offset start --format '%v\n'
{"user": 505, "item": 885445, "topic": 1, "action": "hide", "ts": 1794409760.18}
{"user": 505, "item": 422520, "topic": 1, "action": "hide", "ts": 1794409760.18}

4Prometheus, the metrics collector

A log line tells you about one request. To run a system you also need numbers about all of them, such as how many requests came in, how slow the slowest were, and how many fell back to the safety net. Those numbers are metrics.

4.1Time series and labels

Prometheus stores each metric as a time series, a value recorded again and again over time.7 A metric can carry labels, which are key and value pairs.9 In the lab, feed_hop_seconds{hop="candidates"} and feed_hop_seconds{hop="ranking_model"} are two series of one metric, one for each step of the request. Labels are how one chart can show every step as its own line.

4.2Scraping

Each service publishes its current numbers as plain text at a web address ending in /metrics. Prometheus visits each address on a schedule and records what it finds. This is called scraping, and it means Prometheus pulls the numbers instead of services pushing them.7 The lab scrapes every two seconds. A useful side effect is that if a service dies, Prometheus notices at the next visit, because the address stops answering.

4.3Counters, gauges and histograms

Table 2. The three metric types the lab uses.8
TypeHow it behavesExample in the lab
CounterOnly goes up, or back to zero when the service restartsfeed_requests_total, pages served so far
GaugeGoes up and down freelystream_backlog_events, actions waiting to be processed
HistogramCounts observations into bands, called bucketsfeed_hop_seconds, how long each step took

A counter on its own is not very interesting, since it only grows. What you chart is its rate, such as requests per second over the last 15 seconds. A gauge is charted as it is.

4.4Why a p99 from Prometheus is an estimate

A histogram does not keep every duration. It keeps a count for each band, such as "between 8 and 16 ms". To get the 99th percentile, Prometheus finds the band where the 99th percentile falls and assumes the requests are spread evenly inside it. So the answer is an estimate, and its error is limited by the width of that band.10 A worked example with made-up numbers makes this concrete.

Read Figure 3 with the method above. The 198th request is 4 of the way through 5 requests in the 16 to 32 ms band. Assuming they are spread evenly, the estimate is 16 + (4 ÷ 5) × 16 = 28.8 ms. The real value could be anywhere from 16 to 32 ms. The class rounds the p99 numbers it reads from Prometheus for this reason. Narrower bands give better estimates at the cost of more series to store.

In the lab

The text that Prometheus scrapes is readable by people too. These lines are from the feed service.

# a counter with a label, and a gauge
curl -s localhost:8080/metrics | grep -E '^feed_requests_total|^stream_backlog_events'
feed_requests_total{served_by="full"} 2.0
stream_backlog_events 0.0

Prometheus has its own page at localhost:9090, where you can type a query such as rate(feed_requests_total[15s]) and see the series it returns.

5Grafana, the dashboard

Prometheus holds the numbers, and Grafana draws them. Grafana queries and visualises data from data sources, which are connections to systems that store data.1113 In the lab its one data source is Prometheus. Grafana keeps the dashboards, not the data, so if Prometheus stopped, every chart would go blank.

A dashboard is a set of panels, and each panel shows one visualisation from one or more queries.12 The lab's dashboard is called Feed lab. It refreshes every five seconds and shows the last five minutes.

6One action, end to end

Here is one hide in the lab, following it through all four tools. These steps really do happen in this order, and the class runs them live.

  1. The app tells the feed service that user 505 hid an item from topic 1.
  2. The feed service writes that event to the Kafka topic events and answers at once. It does not wait for anything downstream.
  3. The stream worker, a Kafka consumer, reads the event and adds 1 to the field h:1 in the Redis hash s:505. It also resets the session's time to live to 30 minutes.
  4. On the user's next request, the feed reads s:505 from Redis. Both the user tower and the ranker now see three hides on topic 1. In the recorded run, all three hides were features within 113 ms, and topic 1 went from 16 items on the page to none.
  5. Throughout, Prometheus scrapes the feed and the worker. The stream backlog gauge stays at zero. If the worker stopped, the gauge would climb, and Grafana's Stream backlog tile would show it, while every page still loaded without an error.

That last point is the reason for the whole toolkit. The worst failures in a feed do not raise errors. A stale feed looks healthy to the user and to the error log. Only the numbers show it, and only if someone collects them and puts them where people look.

7Check your understanding

Five questions, one best answer each. Open the answer after you choose.

Q1. The stream worker is stopped for ten minutes, then restarted. What happens to the hides users sent in that time?

  1. They are lost, because nobody read them
  2. They wait in Kafka and are processed after the restart
  3. The feed service writes them to Redis itself
  4. Kafka sends them back to the app to retry
Show the answer

B. Reading does not delete, and the worker resumes from its offset. A is what happens with a simple queue that nobody drains, not with a log. C is the design the log replaced. While the worker is down, pages are stale but load normally.

Q2. Why does the feed read a user's session from Redis and not from Kafka?

  1. Kafka cannot store numbers
  2. Redis keeps data longer than Kafka
  3. A request needs the current session by key, and Kafka is read in order, not looked up by key
  4. Redis is the only one that runs in Docker
Show the answer

C. Kafka answers "what happened, in order", and Redis answers "what is true now, for this key". B misses the point. How long data is kept is a setting in both, and the difference is how you find it.

Q3. Which metric type fits "how many actions are waiting for the stream worker right now"?

  1. Counter
  2. Gauge
  3. Histogram
  4. A label
Show the answer

B. The backlog rises and falls, so it is a gauge. A counter only goes up. A histogram counts how values spread across bands, which fits durations. A label is a tag on a metric, not a type.

Q4. Prometheus reports a p99 of 28.8 ms, and the bands near it are 16 to 32 ms. What can you say about the true p99?

  1. It is exactly 28.8 ms
  2. It is somewhere between 16 and 32 ms
  3. It is at most 16 ms
  4. Nothing, since histograms do not measure time
Show the answer

B. The estimate assumes requests are spread evenly inside the band, so the true value can be anywhere in it. This is why you round such numbers and choose bands that are narrow where you care most, such as around your latency budget.

Q5. Every Grafana panel suddenly shows no data, while the feed still serves pages. What is the most likely cause?

  1. The ranker is down
  2. Redis lost its data
  3. Prometheus stopped, or stopped reaching the services
  4. Kafka is full
Show the answer

C. Grafana stores no metrics, so it has nothing to draw when its data source stops answering. A would show up as a change in panels, not empty ones. Note that this failure hides every other failure, which is why teams also watch the watcher.

8Terms

Consumer
A program that reads events from a Kafka topic.
Dashboard
A set of panels in Grafana, each showing one chart from a query.
Data source
A system Grafana reads data from, such as Prometheus.
Event
A record that something happened, with a key, a value and a timestamp.
Gauge
A metric that can go up and down, such as a backlog.
Counter
A metric that only goes up, such as requests served.
Hash
A Redis value made of field and value pairs under one key.
Histogram
A metric that counts observations into bands, used for durations.
Key
The unique name of an item in Redis, used to read it back.
Label
A key and value pair on a metric that splits it into series.
Offset
A consumer's position in a topic, the number of the next event to read.
Producer
A program that writes events to a Kafka topic.
Retention
How long a topic keeps its events, whether or not they were read.
Scraping
Prometheus visiting each service's /metrics address on a schedule.
Set
A Redis value holding unique items with no order.
Time to live
How long a Redis key lasts before Redis deletes it by itself.
Time series
A value recorded over and over in time.
Topic
A named stream of events in Kafka.
